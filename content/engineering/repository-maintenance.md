# 小型仓库的持续维护与 Agent 协作

适用于已经能运行、还在持续迭代的小型工具和 Mod 仓库。目标不是多加几层流程，而是让下一次修改更容易定位、验证和回退。先从一个反复出问题的模块开始，不必做全仓改造。

## 先找权威实现，再改模块边界

每项配置、运行状态或接口契约都应有一个明确的归属。其他模块可以读取、订阅，或生成供展示的派生结果，但不应独立修改自己的副本。缓存和只读快照不违背这条原则；关键是它们不能反过来决定真实状态。

以两个设置面板为例：先追踪各自的默认值、持久化和生效路径。若两个面板各自写一套设置，先让其中一个改走同一读写接口，保持原有外观、默认值和旧配置兼容。用「从两处修改、重新打开后仍一致」验证，再迁移另一处。确认旧路径没有调用者、回归通过且仍可回退，再删掉旧写入逻辑。不要长期保留两套权威实现。

模块接口应藏住内部复杂度。加载器可以让不同格式通过各自适配器进入同一个协调核心；管理界面读取核心的状态，而不是自己另算一次加载顺序。旧格式的调用顺序和生命周期仍需验证，统一核心不等于兼容性自然成立。只有在真实依赖多次越界时，才考虑增加依赖方向或循环依赖检查。

## 让仓库给 Agent 正确的线索

- **项目说明（如 `AGENTS.md`）**：放模块地图、构建和测试入口、不可破坏的行为，以及反复出现的坑。链接权威文档，不复制整套知识。
- **项目 [Skill](../skills/overview.md)**：放按需执行的流程，如调试、冒烟测试和发布。简单改动走短路径，复杂问题才需要完整诊断。
- **脚本、Hook 或 CI**：负责可机械判定的规则。优先复用现有检查，新增规则先写成可手动执行的脚本，稳定后再决定是否接入自动化。
- **通用开发工具**：提供检索、诊断、证据管理和验证能力。项目的业务规则仍留在项目仓库，不在通用工具里养第二份。

例如，发布前可让脚本检查所有即将公开的提交中的 Author 和 Committer，而不是只看最后一条提交或当前 `git config`。用 [`git var`](https://git-scm.com/docs/git-var) 检查下一次提交的有效身份，再对实际出站提交检查已存储的身份。两种检查回答的是不同问题。报告只指出哪项不符合要求，不回显不应公开的值。

## 选足以支撑结论的验证

调试先复现和收集证据，再验证最可能的根因、做最小修复并重跑原场景。几次修复都失败，先回头检查假设，不继续堆补丁。冒烟测试挑少量关键路径，明确区分通过、失败、偶发失败和证据不足。构建成功不等于业务行为通过；中性夹具也不能代替真实宿主或设备。

性能改动先建立基线，在可比的宿主、输入和场景下定位热点、复测并检查行为一致性。没有可比较的数据，就记为待验证的假设，不记为已获得的收益。保留有用证据，目标已验证后不为增加测试数量继续重复运行。

## 迁移结束后，把旧路收掉

- **先还影响真实工作的债**：优先处理经常修改、反复出错或影响面广的区域，而不是为了整洁重写。
- **每个项目有一个明确的主工作目录**：给缓存、日志和测试产物写清生成方式与保留条件；清理前区分可重建产物与唯一成果，保护未同步代码、真实存档和仍有价值的证据。
- **代码和文档同改**：接口、命令或实际行为变了，就更新对应说明。过时文档若已无用途，删掉比留下冲突答案更好。
- **少量重要决策留痕**：长期生效的决定可写一页简短 ADR（架构决策记录），说明背景、决定、理由和影响。小改动不必另写。

这一套做法可以随日常开发采用：遇到具体问题，确认谁负责、选一个可回退的改动、验证行为、收掉无用旧路。只有反复发生的问题才值得升级为共享组件、测试或规则。

本文是实践建议；设置面板和加载器为说明性示例，不是特定版本的兼容、性能或实机测试报告。
