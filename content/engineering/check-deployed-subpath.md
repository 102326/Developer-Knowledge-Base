# 构建通过，为什么 404 返回后链接却坏了

这座文库部署在域名下的项目子路径，而不是网站根路径。按维护记录，首次公网验收发现：打开不存在的页面，经 404 页返回首页后，再点首页的相对链接，可能会跳到站点根路径。这正是「构建通过」无法单独证明的导航行为。

## 问题不是链接文件不存在

在单页导航中，页面内容切回首页时，地址栏中的 URL 也会参与解析随后的相对链接。浏览器会把不带末尾斜线的 `/project` 的最后一段当作需要替换的路径段，而 `/project/` 是目录。对同一个相对链接，这两个首页地址会产生不同结果：

```js
new URL("./skills/overview", "https://example.com/project").pathname
// "/skills/overview"

new URL("./skills/overview", "https://example.com/project/").pathname
// "/project/skills/overview"
```

`example.com` 是占位域名。代码只计算 URL，不发送网络请求。这说明为什么检查源文件是否存在，无法发现这个问题。

## 修一个入口，测真正的后果

[实际修复与测试](https://github.com/102326/Developer-Knowledge-Base/commit/e2c2b4759ab7f2e6337cfa5c3046cd3dd34f3569)只在 404 页生成返回链接时补齐末尾斜线，不改写每一篇文章的链接。回归测试渲染真实 404 组件、提取首页链接，再计算从该地址点击相对文章链接会去哪里。它覆盖根站点，以及传入配置带或不带末尾斜线的项目子路径。

这种测试验证的是 URL 生成和解析，不等于在浏览器里重新跑过部署。要确认实际部署行为，冒烟测试仍应经过同一条路径：访问不存在的地址 → 从 404 返回首页 → 点击一篇文章 → 确认最终 URL 仍在项目子路径下，且内容能打开。

## 可以复用的排查方法

源文件、构建产物和导航运行是不同层。相对链接只在某条跳转路径失效时，先对比「直接打开」与「从该入口跳转」后的最终 URL；找到差异再改负责生成它的那一层。这样既能写出小而有针对性的回归，也不用把每个文档链接都变成硬编码地址。

本文依据仓库维护记录与公开修复提交。本次另核对了示例中的 URL 解析，没有重新进行公网浏览器回归。
