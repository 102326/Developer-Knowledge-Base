# 怎样判断一个 Skill 真的有用

Skill 能被发现，不代表它会在合适的时候被使用。一次回答正确，也不说明 Skill 带来了改进。用同一批小案例比较两种配置，先弄清差异出在哪，再决定要不要改提示词。

## 先定义什么算做对

沿用[创建与使用 Skill](create-and-use.md)里的 `readme-check`。准备一份没有隐私数据的测试仓库，在 README 放入一个存在的相对文件链接和一个缺失的链接。复用同一份输入，不为不同版本调整预期。

- **正例**：「核对 README 里引用的本地文件，只报告。」两条路径应分别判为存在与缺失，工作区不发生改动。
- **反例**：「帮我润色 README 的开头，不要检查链接。」不应套用路径核查流程。
- **阻断例**：当测试工具无法读取某一目标时，应记为「未核验」，不能将读取失败说成文件不存在。只有实际形成该阻断，才可对这条用例下结论。

文件是否存在、是否改动过、调用是否成功，优先用文件状态和实际活动记录判定。是否选了恰当策略，可以由人复核，也可以用评审模型初筛；评审意见不能替代缺失的执行记录。

## 做一次可解释的对照

1. 如果要评估要不要引入 Skill，用没有该 Skill 的配置对照候选；如果要评估版本升级，就用旧版对照新版。
2. 尽量固定模型、宿主、工作目录、可用工具与输入，在独立会话里分别运行。记下例外，别把改模型或改权限的效果算到 Skill 头上。
3. 如果在测自然触发，两组都用不点名 Skill 的请求。显式调用可以作为单独对照，用于区分「选错流程」和「选对了但执行不好」。
4. 记录结果、能看到的工具轨迹、实际改动和无关操作。行为不稳定时，用相同条件再跑少量轮次并保留原始失败，不用一次成功覆盖失败。

把三种结论分开写：**选用**看宿主能提供的选择证据，**执行**看实际动作，**结果**看是否满足用例预期。宿主没显示选择信息时，标为不可观察，不根据回答反推。耗时只在环境可比且采样足够时比较；在小规模对照里，先看重复调用和无效步骤更实用。

## 根据失败位置改对的那一层

该触发却没触发，先查技能发现和 `description`；触发后路径仍用错，检查正文的路径基准；权限或工具不支持，补足能力或如实报告，而不是再加一句「务必完成」。如果规则能用脚本直接判定，例如「只读任务没有改动文件」，就不必用评审模型猜。

改完先复跑失败案例，再跑一个本来正确的例子，确认没有退步。能解释这次改动解决了什么，就不必为小仓库另建一套大型评分系统。

本文为评测方法与示意案例，不是某个宿主或模型的实际评测结果。进一步阅读：[Agent Skills 官方评测指南](https://agentskills.io/skill-creation/evaluating-skills)。
